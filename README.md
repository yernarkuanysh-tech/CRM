# GrantEd CRM

Рабочая версия для владельца и команды до 10 сотрудников. Интерфейс — React + TypeScript + Tailwind CSS (Vite, папка `src/`), бэкенд — [Supabase](https://supabase.com): вход через Supabase Auth, данные в Postgres, права доступа — row level security. Собственного сервера больше нет: `npm run build` собирает статический сайт в `dist/`, который обращается к Supabase напрямую.

Рекомендуется хранить репозиторий GitHub как **Private**: приложение работает с персональными данными клиентов.

## Первый запуск

1. **Схема базы.** Примените все файлы из `supabase/migrations/` по порядку командой `supabase db push`. Для ручной установки выполняйте их в **SQL Editor** по имени файла; первая миграция рассчитана на пустую базу.
2. **Настройки Auth** (**Authentication → Sign In / Providers → Email**):
   - при включённом **Confirm email** пользователь подтверждает почту перед доступом к данным. Настройте собственный SMTP Supabase для доставки подтверждений внешним пользователям; почта приглашений Resend — отдельный канал;
   - задайте **Minimum password length = 12** — так же, как требовала прежняя версия.
   - В **Authentication → URL Configuration** укажите адрес CRM в **Site URL** (локально `http://127.0.0.1:5173`).
3. **Переменные.** `cp .env.example .env` и впишите URL проекта и publishable key (**Project Settings → API**). Для production-сборки они уже лежат в `.env.production`.
4. `npm install && npm run dev` и откройте http://127.0.0.1:5173.

Сразу после применения миграции создайте владельца: **первая зарегистрированная учётная запись становится владельцем**, все последующие — только по приглашению. Пароль хранит Supabase Auth. База изначально пустая: добавьте клиентов либо нажмите «Импорт из прототипа» в браузере, где использовалась старая версия (только в пустую базу; localStorage не удаляется).

## Возможности

- Клиенты: бакалавриат, магистратура, PhD; поиск, фильтры, страницы по 10 записей.
- Команда: до 10 активных сотрудников и ожидающих приглашений, отдельный пароль для каждого, одноразовая ссылка на 7 дней, отключение доступа владельцем.
- Профиль: направление, страны, семестр и год, финансирование, английский, GRE/GMAT, консультант, дата старта, контакты и до 20 пользовательских тегов.
- Заявки по вузам, статусы, дедлайны, задачи, внутренние заметки.
- Документы абитуриента хранятся в Google Drive; ссылка на папку добавляется прямо в карточке.
- Application fee: сумма, валюта, статус и дата оплаты. Итоги только оплаченных сборов, отдельно по валютам без конвертации.
- WhatsApp: открытие чата по номеру. Прикрепление PDF выполняется вручную; WhatsApp Business API и импорт переписки не подключены.
- Одностраничный PDF по завершении этапа. Итоги, следующий этап, действия клиента, снимок заявок и расходов. До 8 подробных заявок; все заявки учтены в сводке. PDF — изображение высокого разрешения, текст не выделяется. Переполнение блокирует выгрузку.
- Отметки отправки и ознакомления вносятся администратором по фактическому сообщению клиента. Клиентского портала, публичных ссылок подтверждения и автоматической рассылки нет.

## Хранение и восстановление

Данные лежат в Supabase Postgres: таблица `public.clients` (карточка клиента целиком в `data` jsonb, номер версии в `revision`) и служебные таблицы в схеме `private` (профили и роли, приглашения, настройки, хеш резервного кода, журнал действий `private.audit`). Через API доступны только чтение `clients` для активных сотрудников и функции из миграции; запись и все проверки (формат карточки, неизменяемость отчётов, лимит команды) выполняются в базе.

Резервное копирование — средствами Supabase (**Database → Backups**; ежедневные копии есть на платных планах). JSON-экспорт в боковом меню и в настройках включает клиентов, заявки и отчёты, но не пароли и токены. Импорт JSON-файла через интерфейс пока не добавлен.

Каждая карточка сохраняется со своей версией. Если карточку уже изменили в другой вкладке или другой сотрудник, база отклоняет устаревшее сохранение, интерфейс показывает постоянное уведомление; скопируйте введённый текст и обновите страницу перед повторной правкой. Изменения других сотрудников видны после обновления страницы.

## Приглашения сотрудников

Владелец открывает «Настройки → Команда», указывает имя и рабочую почту сотрудника. CRM создаёт одноразовую ссылку на 7 дней и автоматически отправляет её через Supabase Edge Function и Resend. По ссылке сотрудник создаёт собственный пароль; регистрация без действующего приглашения отклоняется базой. Активные сотрудники и ожидающие приглашения вместе занимают не более 10 мест. Владелец может отозвать приглашение или отключить сотрудника; отключение сразу закрывает доступ к данным и завершает его сессии. Если почтовый сервис недоступен, CRM показывает ту же ссылку для ручной отправки.

Для включения автоматической отправки:

1. Создайте API-ключ в Resend и подтвердите домен отправителя.
2. Скопируйте `supabase/functions/.env.example` в `supabase/functions/.env` и заполните `RESEND_API_KEY`, `INVITE_FROM_EMAIL` и публичный адрес CRM в `CRM_SITE_URL`.
3. Загрузите секреты и функцию:

```bash
supabase secrets set --env-file supabase/functions/.env
supabase functions deploy send-team-invite
```

Если CRM показывает `Failed to send a request to the Edge Function`, проверьте доступность функции, её логи и CORS в том же проекте, URL которого указан в `VITE_SUPABASE_URL`. Сетевая ошибка не доказывает, что сервер ничего не сделал: CRM не создаёт второе приглашение автоматически после неоднозначного сбоя. Для подтверждённого HTTP 404 доступна ручная ссылка. Повтор одной попытки использует тот же токен и ключ идемпотентности Resend; отдельная повторная отправка заменяет ссылку. «Принято почтовым сервисом» означает принятие запроса Resend, а не доставку в почтовый ящик.

Приглашённый пользователь с существующим аккаунтом входит со своим паролем; сервер проверяет подтверждённый email, текущую сессию и токен. После успешного принятия приглашение исчезает из ожидающих, а сотрудник появляется в команде. Отключённый участник включается владельцем через список команды, приглашение не обходит блокировку.

Секрет Resend хранится только в Supabase и никогда не попадает в браузер или GitHub.

## Публикация

Нужен любой статический хостинг с HTTPS: соберите `npm run build` и опубликуйте папку `dist/`. Маршрутизация в адресе после `#`, поэтому дополнительных правил не требуется. Docker-образ (`Dockerfile`) собирает интерфейс и отдаёт его через nginx на порту `PORT` (по умолчанию 3000) — так CRM разворачивается на Railway из CI. Для VPS в PS.kz — [`deploy/pskz/README.md`](deploy/pskz/README.md). После публикации добавьте адрес сайта в **Site URL** и **Redirect URLs** в настройках Supabase Auth.

## Разработка

- `npm run dev` — Vite-сервер с горячей перезагрузкой на http://127.0.0.1:5173.
- `npm run build` — проверка типов TypeScript и production-сборка в `dist/`; `npm start` — просмотр собранной версии на http://127.0.0.1:3000.
- `npm run typecheck` — только проверка типов.
- Изменения схемы — новым файлом в `supabase/migrations/`.

Структура интерфейса: `src/pages` — экраны, `src/forms` — модальные формы, `src/components` — общие элементы, `src/lib` — расчёты fees, отчёты и PDF без зависимости от React, `src/lib/api.ts` — клиент Supabase, `src/state.tsx` — сессия и сохранение данных. Стили — утилиты Tailwind с токенами темы в `src/styles.css`; Preflight отключён, чтобы сохранить исходные отступы браузера.

## Проверки

`npm test` — бизнес-расчёты, отправка приглашений с подставным провайдером, все миграции в PGlite/PostgreSQL, RLS и серверные RPC (Vitest, `tests/web`). `npm run test:pdf` — реальная генерация PDF и переполнение, Canvas установлен как dev-зависимость. CI проверяет сборку, тесты, PDF, типы и lint Edge Function. Frontend ESLint отдельно не настроен.

Для ручной QA-проверки: `node tests/support/qa-server.ts`, затем в другом терминале `VITE_SUPABASE_URL=http://127.0.0.1:54329 VITE_SUPABASE_PUBLISHABLE_KEY=qa-public-test-key npm run dev -- --port 4175 --strictPort --mode qa`. Вход: `qa-owner@example.invalid` / `QA-only-password-123`. Это синтетический пароль, действующий только в тестовой базе в памяти. Тестовый сервер принимает аккаунты `example.invalid`, подменяет Auth/почту, исполняет настоящие миграции и SQL CRM. Перезапуск удаляет только тестовую базу из памяти.

Push и pull request запускают проверки. Production-сборка контейнера и Railway-деплой запускаются только вручную через `workflow_dispatch` с `deploy=true`, после успешных тестов. Самостоятельные триггеры хостинга вне GitHub Actions контролируются в настройках хостинга.

## Настройки и восстановление пароля

Раздел «Настройки» позволяет задать имя администратора, название организации и год набора для новых карточек. Смена пароля требует текущий пароль и завершает все сессии. В разделе восстановления создайте резервный код и сохраните его отдельно: показывается один раз, в базе хранится только хеш. Новый код отменяет предыдущий. На странице входа «Забыли пароль?» принимает почту, код и новый пароль. Использованный код удаляется, все сессии завершаются. После восстановления создайте новый код. Почтовая рассылка для восстановления не используется; без заранее созданного кода этот способ недоступен.

В карточке → «Тесты» и на вкладке информации можно добавлять результаты и пересдачи IELTS (0–9, шаг 0,5), TOEFL iBT (1–6, шаг 0,5 либо 0–120, целые) и DET (10–160, шаг 5). Хранятся общий балл и необязательная дата сдачи; автоматического пересчёта шкал нет. Новые поля не меняют старые карточки и снимки отчётов.
