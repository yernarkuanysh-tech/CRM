# Технический аудит CRM — 13 октября 2026

## Система и план проверки

React/TypeScript + Vite → Supabase Auth, PostgREST/RPC, private Storage и Edge Function `send-team-invite` → Resend. Карточки в `public.clients.data` JSONB, optimistic concurrency по `revision`. Профили, роли, приглашения, настройки и журнал действий находятся в `private`. База рассчитана на одну организацию; многопользовательская изоляция организаций не реализована и не заявляется.

План по реальному коду: проверить все миграции и RPC на изолированной базе; пройти создание/редактирование карточки, теги, заявки/статусы/сборы, задачи, отчёты и удаление; проверить Auth/сессии и owner/staff/RLS; проследить создание, письмо и принятие приглашений; проверить конфигурацию, CI, сборку, типы, тесты и доступные UI-сценарии.

| Модуль | Реализованное поведение |
| --- | --- |
| Абитуриенты | Создание, редактирование, owner-only удаление, поиск/фильтры/теги; архивирования нет |
| Ответственный | Текстовое поле `consultant`, без FK на сотрудника и отдельного разграничения по ответственному |
| Заявки | Университет/программа/дедлайн/статус, application fee; статус карточки выводится из заявок |
| Задачи | Вложены в карточку, добавление и выполнение, общий список |
| Документы | Ссылка Google Drive; прежний private Storage сохранён для старых файлов и очистки |
| Отчёты | Снимок состояния, A4 PDF, ручные отметки отправки и ознакомления |
| Команда | Owner/staff, 10 мест для сотрудников и ожидающих приглашений, отзыв/отключение/роли |
| Интеграции | WhatsApp — ссылка `wa.me`; Gmail OAuth, WhatsApp API и автоматические уведомления отсутствуют |

## Найдено и исправлено

1. **Неоднозначные ошибки Edge Function.** `FunctionsFetchError`/relay нельзя считать отсутствием функции: запрос мог выполниться до потери ответа. Автоматическое создание второго приглашения после такого сбоя убрано. Ручной fallback допустим только для явного 404. Ошибка не выдаётся за успех.
2. **Повторы и токены.** Попытка имеет 256-битный токен; повтор не обновляет запись и срок. Запрос к Resend использует ключ идемпотентности. Новая явная повторная отправка заменяет предыдущую ссылку. Поздний ответ отправителя не отмечает новый токен как отправленный.
3. **Существующий аккаунт.** Страница приглашения поддерживает вход вместо повторной регистрации. `accept_invitation` проверяет подтверждённый email в `auth.users`, текущую сессию, срок, однократность и отсутствие членства. Роль назначается сервером, всегда staff.
4. **Лимит команды.** Приглашения и регистрации используют тот же advisory lock, что изменения ролей/доступа. Проверка количества мест больше не является несогласованной с остальными операциями. Многосессионная гонка отдельно не воспроизводилась в PGlite.
5. **Приглашение при активной сессии.** Открытие `#invite/...` не теряется при уже выполненном входе. Добавлены загрузка, понятные ошибки и обработка ожидания подтверждения почты.
6. **Сессии.** Единый серверный предикат проверяет активный профиль, подтверждённый email и существование `session_id` в `auth.sessions`. Завершённая сессия не получает доступ по оставшемуся JWT. Отключённый владелец не восстанавливает доступ резервным кодом; одноразовый код блокируется при проверке.
7. **Формы и сохранение.** Защита от повторной отправки добавлена до первого await. Чекбоксы задач и селектор статуса заявки показывают сохранённое состояние после отказа backend. Без абитуриентов нельзя открыть бесполезную форму задачи. Ошибку начальной загрузки можно повторить.
8. **Серверная валидация.** Пропущенные поля больше не обходят проверки через SQL NULL. Проверяются календарные даты, задачи и заявки. Историю отчётов и сохранённые отметки нельзя переписывать/удалять через API; ознакомление требует отправки и подтверждения. На frontend запрещена невозможная дата application fee.
9. **Старые файлы.** Ошибка удаления файла перестала игнорироваться; очистка проходит все страницы Storage по 1000 файлов. FK удаляет метаданные документов с карточкой. Ошибка физической очистки сообщается отдельно.
10. **CI и секреты.** Исправлен пользователь GHCR login, деплой отделён от push/PR и зависит от тестов. Локальные env-файлы и временные файлы Supabase исключены из Git. Publishable key остаётся публичным по назначению; реальные секреты в коммит не добавлялись.

## Почему возникала ошибка приглашения

`Failed to send a request to the Edge Function` означает транспортный сбой браузерного вызова. Ранее endpoint был проверен с ответом 404. При этом аудите он уже отвечает **401 без Authorization**, а OPTIONS — **204** с нужными CORS-заголовками. Поэтому отсутствие deployment или CORS нельзя объявить подтверждённой текущей причиной. В коде достоверно отсутствовали безопасные повторы и корректная обработка транспортного сбоя.

Подключённый Supabase-аккаунт не имеет доступа к проекту приложения: metadata/список функций недоступны. Проверить текущие logs, секреты и Auth Redirect URLs нельзя. Автоматическая доставка остаётся внешним блокером до проверки этих параметров:

- функция `send-team-invite` и её deployment/logs в проекте, указанном в `VITE_SUPABASE_URL`;
- `RESEND_API_KEY`, `INVITE_FROM_EMAIL`, `CRM_SITE_URL` в Edge Function Secrets;
- подтверждённый домен отправителя и ограничения Resend;
- публичный CRM URL в Site URL / Redirect URLs Supabase Auth;
- собственный SMTP Auth, если включено подтверждение email.

Секреты должны вводиться в Supabase/Resend, не в чат или Git. Новая миграция и Edge Function подготовлены и проверены локально; production-деплой не выполнялся. После отдельного применения миграции необходимо обновить Edge Function для передачи токена при записи статуса отправки. Старый deploy письма сможет отправлять, но запись статуса с прежним аргументом станет ошибкой; frontend показывает предупреждение.

## Проверки и границы доказательств

- TypeScript `--noEmit`, production Vite build — успешно.
- **41 автоматический тест**: расчёты, HTML-экранирование PDF-отчёта, обработчик приглашений/почтовые ошибки, токены, RPC/доступ, все миграции, постраничная очистка файлов. Пропущенных тестов нет.
- Отдельный Canvas/PDF-тест — успешно: одностраничный A4 и блокировка переполнения.
- Deno check Edge Function с закреплёнными зависимостями и Deno lint — успешно.
- npm при установке dev-зависимостей: 0 выявленных уязвимостей. Общий frontend ESLint до аудита не был настроен.
- PostgreSQL/PGlite выполняет реальные SQL/pgcrypto/RLS; платформенные таблицы Auth/Storage и JWT-функции создаются тестовым стендом. Это не end-to-end проверка управляемого Supabase Auth, SMTP или Resend.
- UI на localhost с изолированным QA API: вход владельца; создание карточки, два тега, ответственный и Drive-ссылка; заявка/оплаченный fee/оффер; задача/выполнение; сохранение после reload; отправка с подставным провайдером; ссылка при активной сессии; недействительность использованного токена; вход сотрудника и отсутствие административных блоков.
- Регистрация тестового сотрудника выполнялась через локальный QA API; через UI проверялись форма ссылки и последующий вход. Удаление и доступ к Storage проверены автоматически, реальные Google Drive/WhatsApp не открывались.
- Реальные письма и delivery webhooks, production-данные и production-удаление не использовались.
- Осталось предупреждение Vite: основной bundle больше 500 kB. Для текущего порядка 100 карточек это не подтверждённая критическая проблема; отдельное разделение bundle не входило в исправления.

CI теперь выполняет расширенные проверки и пропускает deployment job на обычном push. Внешние автоматические deployment-триггеры хостинга нельзя проверить без доступа к его настройкам.
